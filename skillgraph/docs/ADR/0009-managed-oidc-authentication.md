# ADR-0009: Managed OIDC identity provider behind a replaceable adapter

Status: **Accepted** for the approach (owner Decisions 3 and 6, 2026-11-23): managed OIDC, no locally stored user passwords, SKILLGRAPH-owned roles, organisations and API keys, and real OIDC integration tests in an isolated environment. **The provider (ZITADEL Cloud vs Amazon Cognito) is NOT selected**; see [IDP_COMPARISON.md](../IDP_COMPARISON.md), decision U-5.
Date: 2026-11-23 (revised)
Supersedes: ADR-0004 (first-party password authentication)

## Context
The owner approved a managed, standards-based OIDC provider. SKILLGRAPH must store no user passwords. Its own roles, permissions, organisations and API keys stay in SKILLGRAPH. The integration must be modular so the provider can be replaced, and authentication must never be faked.

Requirements still in force: email verification, account recovery, MFA for privileged roles, session revocation (PRD §19); OIDC-compatible authentication (PRD §13); organisation-scoped authorization enforced by SKILLGRAPH (PRD §20).

## Decision (provider-neutral)
1. **Protocol.** OIDC Authorization Code flow with PKCE. SKILLGRAPH's API is a confidential client (backend-for-frontend), using the `openid-client` library (v6.9.1 at review). The provider is configured only by issuer URL (discovery), client ID and client credential.
2. **No IdP tokens in the browser.** After the callback, the API validates the ID token (JWKS signature, `iss`, `aud`, `azp`, `exp`, `nonce`) and creates **its own server-side session**: an opaque `__Host-` cookie, stored hashed. IdP access, refresh and ID tokens are neither stored nor sent to the browser.
3. **Identity linking.** Users are keyed by (`issuer`, `sub`) in `external_identities`. Email is copied only when `email_verified = true` and is never used to link accounts automatically.
4. **Authorization stays in SKILLGRAPH.** Roles, organisation membership, issuer approval, consent and API keys live in SKILLGRAPH's database. Nothing authorization-relevant is stored in the IdP.
5. **MFA for privileged roles.** The IdP performs MFA. SKILLGRAPH checks `amr`/`acr` and `auth_time` before privileged actions, and requests step-up (`acr_values`, `max_age`, `prompt=login`) when they're insufficient. Provider behaviour is verified in spike S-6. The fallback is an IdP policy requiring MFA for all privileged users.
6. **Logout and revocation.** Local session revocation, RP-initiated logout, and OIDC Back-Channel Logout where the provider supports it.
7. **Provider-specific code in one adapter.** `IdentityProviderAdmin` handles deleting a user, fetching a profile (data export) and, optionally, provisioning an organisation's SSO. One implementation per provider. Login itself is generic OIDC.
8. **Switching providers** means new client configuration, a new admin adapter, and an audited re-linking procedure, because `sub` values change. It's documented as a runbook and never automatic.
9. **Email.** The IdP sends verification, recovery and MFA email. SKILLGRAPH sends only application email (invitations, notifications) via `EmailTransport` (SES in Singapore, D-6).
10. **Machine-to-machine access** uses **SKILLGRAPH-issued API keys** (owner Decision 5; [ADR-0012](0012-api-keys.md)). The IdP isn't involved.
11. **Testing: real OIDC integration tests in isolated environments** (owner Decision 6). Production code has no authentication bypass, "dev login" or hard-coded user.

    | Layer | Where | Identity provider used | Runs |
    |---|---|---|---|
    | L1 protocol and integration | CI job, isolated network, ephemeral | **A real OIDC server**: if ZITADEL is chosen, the **ZITADEL open-source container** (same product); if Cognito, `oidc-provider` (v9.15.1, a standards-compliant OIDC server) | Every pull request |
    | L2 provider integration | Dedicated **isolated test tenant** at the chosen provider (ZITADEL test instance, or a Cognito test user pool in a separate AWS test account), never shared with dev or prod | The real managed provider | Nightly and before every release |
    | L3 end-to-end | Staging environment | Real provider staging tenant | Before release (Phase 1 exit) |

    - L2 and L3 create **synthetic test users** through the provider's admin API at test start and delete them at the end. TOTP secrets for MFA tests are generated by the harness and never reused.
    - Test credentials live in a GitHub Environment (`oidc-integration`) with restricted access, never in the repository.
    - A test that can't reach its provider **fails or is reported as skipped with the reason**. It's never counted as passed.
    - Production config validation rejects non-HTTPS issuers and `localhost` redirect URIs. Test fixtures live only under `test/`, outside the application bundle.

## Consequences
- The data model has no password, MFA-secret or verification-token tables (DATA_MODEL §1).
- L2 and L3 tests can't run until the owner chooses a provider (U-5) and creates the isolated test tenant. Until then, only L1 runs, and that limitation is reported.
